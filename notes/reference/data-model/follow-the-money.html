Can you follow a dollar from the school budget to the Town’s books?

Yes — for one document, one year, one period. The key that joins the two sides is real, and it is already in the extracted data. It is lost when the database is built, which is why nothing downstream of the database can see it.

Holds

Inside the district’s documents. Budget lines, their figures and the workbook all join on line_key. 8,598 of 8,598.

Holds

Inside the Town’s ledger. Every snapshot resolves to an account, and every account to a fund. 983 of 983.

Holds

Provenance. Every figure in every fact table carries the document it came from. 100%, no exceptions.

Holds, in the CSV

Budget line to ledger account. munis-ledger.csv carries a function column. 41 of the budget’s 45 function codes appear in the ledger. 270 rows, FY2026 period 12.

Lost in the database

The account table has no function column. The key is dropped when lunenburg.db is built, so crosswalk is empty and every API view is blind to a join the data supports.

“Budget versus actual” already exists — and it is not what it sounds like

Two views carry that name. Both join a table to itself:

v_line_budget_vs_actual

budget_figure → budget_figure, pivoting stage

“Actual” here is stage='actual' — a prior year restated by the district inside its own later budget document. 3,453 such rows, FY2014–FY2025.

v_workbook_budget_vs_actual

workbook_figure → workbook_figure, same row, same doc_id

Budget and actual columns of the same workbook. The comparison never leaves the document.

v_appropriation_vs_spend

ledger_snapshot → account, WHERE period = 13

Returns zero rows. Period 13 is the closing period; the only ledger periods held are 9 and 12. A published endpoint that cannot answer with the data behind it.

So the district comparing itself to itself is available and real. The Town’s books compared to the district’s budget is not available at all, and no view attempts it.

What would fix it — and it is not a request to the Town

Load the column that is already there. munis-ledger.csv has a function field; account does not. Carrying it through build_db.py would let crosswalk be populated by code, and would give every API view the join it currently cannot express.

Two limits stay real after that. The code joins a category, never a line: MUNIS gives MS GUIDANC and HS GUIDANC, both coded 2710, where the budget has a row per school — and account names are truncated to ten characters, so matching them by name is inference, not tracking. And coverage is one document: FY2026 period 12 only. Every earlier year is PDF-derived and carries no code at all.

Two things found on the way

A published table with no provenance. variance_by_group holds 57 rows of budget against spend by function group. It has no doc_id column, no script in the repository builds it, and neither fact table can produce its figures. Where those numbers came from is currently not answerable — which is the one thing every other figure here can do.

Vendor data in the published database. fund_1301_cash_journal has 57 rows with a populated vendor column and 136 with comments, and lunenburg.db is served from the site. Athletics officials are paid as individuals. The values were deliberately not read while establishing this — checking them is a local job, not one to do through a model.
